# Adding a New Contract to the Workspace

This guide walks through every step needed to add a new Soroban smart contract
to the workspace. Use it when building a new feature contract such as a
timelock, airdrop distributor, or staking contract.

---

## Step 1 — Create the crate and register it in the workspace

### Create the crate

```bash
cargo new --lib contracts/mycontract
```

This creates `contracts/mycontract/src/lib.rs` and
`contracts/mycontract/Cargo.toml`. Open `contracts/mycontract/Cargo.toml` and
add the `cdylib` crate type (required for Soroban WASM output):

```toml
[package]
name = "mycontract"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib", "rlib"]
```

### Register in the workspace

Open the root `Cargo.toml` and add the new path to the `members` list:

```toml
[workspace]
resolver = "2"
members = [
    "contracts/vesting",
    "contracts/multisig",
    "contracts/token",
    "contracts/mycontract",   # ← add this line
]
```

Verify the workspace sees it:

```bash
cargo metadata --no-deps --format-version 1 | grep '"name"' | grep mycontract
```

## Step 2 — Add the soroban-sdk dependency and testutils feature

The workspace already pins `soroban-sdk`. Reference it from the workspace in
`contracts/mycontract/Cargo.toml`:

```toml
[dependencies]
soroban-sdk = { workspace = true }

[dev-dependencies]
soroban-sdk = { workspace = true, features = ["testutils"] }
```

The `testutils` feature is a dev-only dependency. It enables `Env::default()`,
`Address::generate()`, `mock_all_auths()`, ledger manipulation helpers, and the
test client generated by `#[contractimpl]`. Do **not** enable `testutils` in
`[dependencies]`; it must remain dev-only to keep the WASM build lean.

If your contract needs to call another contract in tests (for example,
deploying a real `TokenContract` to test transfers), add that crate as a
dev-dependency too:

```toml
[dev-dependencies]
soroban-sdk = { workspace = true, features = ["testutils"] }
token = { path = "../token", features = ["testutils"] }
```

## Step 3 — Write the first test

Replace the contents of `contracts/mycontract/src/lib.rs` with a minimal
contract skeleton and a smoke test:

```rust
#![no_std]

use soroban_sdk::{contract, contractimpl, Address, Env, symbol_short, Symbol};

const ADMIN: Symbol = symbol_short!("ADMIN");

#[contract]
pub struct MyContract;

#[contractimpl]
impl MyContract {
    pub fn __constructor(env: Env, admin: Address) {
        env.storage().instance().set(&ADMIN, &admin);
    }

    pub fn get_admin(env: Env) -> Address {
        env.storage()
            .instance()
            .get(&ADMIN)
            .expect("not initialized")
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use soroban_sdk::{testutils::Address as _, Env};

    fn deploy() -> (Env, Address, Address) {
        let env = Env::default();
        env.mock_all_auths();
        let admin = Address::generate(&env);
        let contract_id = env.register(MyContract, (admin.clone(),));
        (env, contract_id, admin)
    }

    #[test]
    fn test_constructor_sets_admin() {
        let (env, contract_id, admin) = deploy();
        let client = MyContractClient::new(&env, &contract_id);
        assert_eq!(client.get_admin(), admin);
    }
}
```

Run the test to confirm everything compiles and passes:

```bash
cargo test -p mycontract
```

## Step 4 — CI build and test steps

The CI pipeline (`ci.yml`) runs `cargo test --all` and
`stellar contract build`, both of which pick up every workspace member
automatically. No changes to `ci.yml` are required for a standard new contract.

The commands that will now cover your contract:

| Command | What it checks |
|---------|---------------|
| `cargo test --all` | All unit and integration tests |
| `cargo fmt --all -- --check` | Rust formatting |
| `cargo clippy --all --target wasm32v1-none -- -D warnings` | Lints (including no-std compatibility) |
| `stellar contract build` | Compiles every member to WASM |

> **Note:** `cargo clippy --all --target wasm32v1-none` compiles for the
> `wasm32v1-none` target. Code that uses `std` will fail here. Keep all
> contract code inside `#![no_std]` crates. Test modules (`#[cfg(test)]`) are
> exempt because they only compile for the host target.

If your contract requires a custom CI step (e.g. a snapshot test or a
separate deploy script), add a new step to the `contracts` job in
`.github/workflows/ci.yml` after the existing `cargo test` step.

## Step 5 — Update the README architecture diagram

The README contains an "Architecture" section with a contract list and a
repository layout diagram. Update both:

### Contract list

Find the contracts table (search for `| Token |` or `| Vesting |`) and add a
row for your new contract:

```markdown
| MyContract | `contracts/mycontract/` | One-line description of what it does. |
```

### Repository layout

Find the `contracts/` block in the directory tree and add your crate:

```
contracts/
├── token/
├── vesting/
├── multisig/
└── mycontract/        ← add this line with a short comment
```

### CONTRIBUTING.md link

If you are creating a contract that other contributors might extend, add a
brief mention and link from `CONTRIBUTING.md` under "Project Structure".

## Checklist

Before opening a PR for a new contract:

- [ ] `contracts/mycontract/Cargo.toml` has `crate-type = ["cdylib", "rlib"]`
- [ ] Root `Cargo.toml` lists `"contracts/mycontract"` in `members`
- [ ] `soroban-sdk` is a workspace dependency; `testutils` is dev-only
- [ ] At least one `#[test]` exists and `cargo test -p mycontract` passes
- [ ] `cargo test --all` passes (no regressions in other contracts)
- [ ] `cargo fmt --all -- --check` passes
- [ ] `cargo clippy --all --target wasm32v1-none -- -D warnings` passes
- [ ] `stellar contract build` succeeds (produces a `.wasm` file)
- [ ] README architecture diagram updated
- [ ] `contracts/mycontract/README.md` created (function reference, storage keys, events)
- [ ] `CHANGELOG.md` updated under `[Unreleased]`
